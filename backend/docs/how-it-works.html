Little Buddy backend, step one

How the toy proves it is a toy

Every answer a Little Buddy gives costs its family one credit, so a device that cannot prove who it is could spend other people's money. This page walks through the device registry, the signing protocol, the pairing flow, and the parent side that owns it all.

The shape of it

Three parties talk to one backend. The toy (an ESP32-S3 with a mic, a screen, a speaker and one button) is deliberately thin: it records, streams and plays. The parent uses a web dashboard to pair toys, pick a child, pause a toy, and later to buy credits. An operator provisions batches at the factory and holds the kill switch. Postgres is the durable truth; Redis holds only short-lived state that can vanish.

Three doors, three keys

The colour of a lane is used consistently on this page: device for anything the toy does, parent for the dashboard, admin for operators.

SurfaceWhoProofWhy that proof
/v1/* deviceThe toyHMAC-SHA256 signature over each request, keyed by a per-device secret flashed at the factoryA microcontroller can do one HMAC cheaply; it cannot safely hold a long-lived bearer token that would be replayable if copied.
/api/* parentParent web app15-minute JWT plus a rotating refresh tokenBrowsers are good at bearer tokens; short access tokens mean removing a parent takes effect within minutes.
/admin/* adminOperatorsOne shared ADMIN_TOKEN, compared in constant timeInternal only, few callers, no self-service; a proper operator login can replace it later.

Nothing that provisions a device is reachable over HTTP. Secrets travel from the CLI into a factory manifest file and from there onto the toy, never through an endpoint.

A device's life

A toy is in exactly one of four states. Every transition goes through one module, devices/registry.js, which also writes a row to device_events, so the history of any toy can be read back for support.

What a toy is allowed to do depends only on its state. A toy that is not yet claimed, or that a parent has paused, still needs to talk to the server so its screen can say why it is quiet:

StatePOST /v1/heartbeat/v1/streamOn the toy's screen
provisioned200, heartbeat_interval_s: 5403 device_not_claimed"waiting for a grown-up"; polls fast so pairing shows within seconds
active200, heartbeat_interval_s: 60allowednormal face
disabled200, status: "disabled"403 device_disabledsleeping face, keeps checking
revoked403 device_revoked403sleeping face

The heartbeat therefore doubles as the pairing-status poll: no separate endpoint is needed.

Born at the factory

npm run provision -- --label 2026W38A --count 500 --hardware-rev r1 creates a batch. For each toy it generates three things in memory: a uuid device_id, a random 32-byte secret, and an 8-character claim code. Only transformed versions of the last two reach the database.

Why the secret is encrypted, not hashed

To verify an HMAC the server must compute it with the real key, so hashing is impossible. Instead the secret is sealed with AES-256-GCM under a subkey derived (HKDF) from the DEVICE_KEK environment variable, with the device id as associated data so a ciphertext cannot be transplanted between rows.

Why the claim code is hashed with a pepper

Eight characters from a 30-letter alphabet is about 39 bits: fine against online guessing behind a rate limit, trivial to brute-force from a plain hash of a leaked dump. A second HKDF subkey acts as the pepper, so a dump without the KEK is useless there too.

Why the manifest is written inside the transaction

The batch commits only after the file is written and fsynced. If the write fails, the rows roll back, so a device can never exist whose secret was lost. The file is opened with wx: an existing manifest is evidence, never overwritten.

The alphabet on the card

ABCDEFGHJKMNPQRSTVWXYZ23456789: no I L O U 0 1, the characters a tired parent misreads. Printed as XXXX-XXXX; entry is case-insensitive and ignores spaces and dashes.

Claimed by a parent

A parent logs in, types the code from the card, and optionally picks which child the toy belongs to. The server normalizes the code, hashes it with the pepper, and looks the row up for update so that two parents racing on the same code are serialized: the second one finds the row already active and gets the same answer as a wrong code.

Unknown, already used, and revoked all look the same. The dashboard gets 404 claim_code_invalid for every failure that is not a malformed code, so a guesser learns nothing about which codes exist. Combined with ten attempts per hour per account, 39 bits is more than enough for a code that can only bind a toy to the guesser's own traceable account.

Unpairing (DELETE /api/devices/:id) returns the toy to provisioned with the same claim hash, so a gifted or resold toy is claimed with the card it came with. For a lost card, an operator can reissue a fresh code, which kills the printed one.

Signing a request

Every request the toy makes to /v1/* carries four headers. The signature covers the method, the path, the toy's identity, the time, a one-time nonce and a hash of the exact body bytes, so a captured request cannot be altered, moved to another path, or sent again.

HeaderValue
X-LB-Devicethe device id (uuid)
X-LB-TsUnix time in seconds, decimal
X-LB-Nonce32 lowercase hex characters, 16 random bytes, never reused
X-LB-Sig64 lowercase hex characters: hex(HMAC-SHA256(secret, canonical))

The canonical string is seven fields joined by a single newline, no trailing newline:

LB1
<METHOD>          uppercase, e.g. POST or GET
<PATH>            path only: no host, no port, no ?query
<device_id>
<ts>              the same bytes as X-LB-Ts
<nonce>           the same bytes as X-LB-Nonce
<body_sha256>     lowercase hex; for no body:
                  e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855

LB1 is a version tag so a future format cannot be confused with this one. The path excludes the query string on purpose: on the WebSocket upgrade the signature itself travels in the query, so the query cannot be part of what is signed. Everything is hex because a microcontroller produces raw bytes and hex needs no padding and no URL escaping.

A worked example

With secret 0123…cdef (64 hex chars), device 3f9c2a7b1e5d8c04, timestamp 1789000000 and nonce 7c1e0f5a9b3d4e2f8a6c1b0d9e7f5a3c, a POST /v1/heartbeat whose body is exactly {"fw":"1.0.0","uptime_s":42} signs as:

body sha256   8a84e1abb3809813bf335b67de12e6c7a5ccb513801bb4bcf9a341e063e173e1
canonical     "LB1\nPOST\n/v1/heartbeat\n3f9c2a7b1e5d8c04\n1789000000\n7c1e…5a3c\n8a84…73e1"
X-LB-Sig      1fb702f7ee187154633c9679c4b8f609bed3e2a9601a92ab60dae0fa28abf5e6

These vectors live in tests/fixtures/hmac_vectors.json. The server's own signer (devices/signing.js), the simulated device used by the tests, and the firmware all have to reproduce them byte for byte; any drift between "what firmware should do" and "what the server checks" fails a test instead of a toy in a child's hands.

For the firmware, in ten steps

  1. Keep the 32-byte secret from the manifest in encrypted NVS; never send it anywhere.
  2. ts = time() + offset, where the offset comes from GET /v1/time or from any 401 body.
  3. Nonce: 16 bytes from esp_random(), hex-encoded lowercase.
  4. SHA-256 the exact body bytes you will send; no body means the empty hash above.
  5. Build the canonical string exactly as shown. No trailing newline.
  6. mbedtls_md_hmac(SHA256, secret, 32, canonical, len, out); hex-encode the 32 bytes lowercase.
  7. HTTP: send the four headers and the exact body from step 4.
  8. WebSocket: sign GET /v1/stream and put the four values in the query string.
  9. On auth_ts_skew: update the offset from server_time, sign again with a new nonce, retry once. On any 403: sleeping face, keep heartbeating.
  10. Check against the two reference vectors before touching a real server.

What the server checks, in order

The verifier in devices/hmac_auth.js runs the cheap checks first so junk traffic costs nothing, keeps a spray of bad requests away from the database, and writes the nonce last so that only a request that has already proven itself can touch Redis. The same function guards both HTTP requests and the WebSocket upgrade.

  1. ShapeIs the id a uuid, the timestamp digits, the nonce 32 hex, the signature 64 hex? No I/O.
    401 auth_missing
  2. Clock window|server now − ts| must be at most 300 s. No I/O. The rejection carries server_time.
    401 auth_ts_skew
  3. Failure countersRedis: 30 failures per minute per device id, 60 per minute per IP for ids that do not exist. Over the limit means no database lookup at all. Redis down means devices fail closed (503), because an unverifiable turn would spend money.
    429 rate_limited
  4. Load the rowPostgres: fetch the device, unseal its secret (and the previous secret, if a rotation is inside its 7-day grace).
    401 auth_unknown_device
  5. SignatureRecompute the HMAC over the canonical string and compare in constant time against the current secret, then the previous one. The body hash comes from the raw request bytes, captured before JSON parsing.
    401 auth_bad_signature
  6. NonceRedis SET dev:nonce:<id>:<nonce> 1 NX EX 900. A second request with the same nonce loses here, no matter how valid its signature.
    401 auth_replay
  7. StatusA revoked device is refused everywhere. Routes that spend money add requireActive: provisioned and disabled toys get a 403 that names the reason.
    403 device_*

A 401 means "prove who you are again": the toy resyncs its clock or makes a new nonce and retries once. A 403 means "we know who you are and the answer is no": the toy shows a sleeping face and keeps heartbeating. Auth failures never produce speech, only a face.

DEVICE_AUTH=off exists for local development and is refused in production. It skips steps 2, 3, 5 and 6 but still requires a real X-LB-Device, so every status rule behaves exactly as it will with auth on. Turning auth off never turns authorization off.

Clock and nonce, and why 900 is bigger than 600

An ESP32 has no battery-backed clock. Its time comes from NTP, drifts between syncs, and is nonsense for the first seconds after boot. The protocol tolerates all of that with two numbers that are chosen together.

  • Skew window 300 s: wide enough for NTP drift between syncs, narrow enough that a captured request goes stale within minutes.
  • Nonce TTL 900 s: strictly more than twice the window. If Redis lost a nonce early, the timestamp check would still reject the replay once the window closed; that is accepted degradation, not a hole worth a second store.
  • Resync: every 401 and 403 body carries server_time, and GET /v1/time answers without auth, so a toy with a wrong clock fixes itself from the very response that refused it.

The stream and the kill switch

Audio flows over a WebSocket at /v1/stream. The upgrade is signed exactly like a GET with an empty body, and the four values ride in the query string because most embedded WebSocket clients (and every browser) cannot set headers on an upgrade. Headers are accepted too, for clients that can.

A verified upgrade is answered with {"type":"ready"}; any device that is not revoked gets a socket. What a button press may do is decided per turn: the toy sends turn_start, the ask gate checks that the toy is claimed and active and that its family still has a credit (counting turns already in flight), and answers turn_accepted or turn_denied {emotion, say}. The refusal never carries a reason, and a paused toy and an out-of-credit family get byte-identical refusals: to the child both are "time for a little break". Audio frames flow during the turn; on turn_end the (currently mock) pipeline produces an answer {emotion, say}, and only after that is sent does the server write the turn as completed and append a single debit row to the family's append-only ledger, idempotent on the turn id. Cancel, timeout, a dropped socket and the kill switch all end a turn as abandoned with nothing charged. The interesting part is what happens when a parent presses pause while the toy is mid-stream:

Parent pause parent

  • Disables and re-enables their own toys only; another family's device id is a plain 404.
  • Unpair returns the toy to provisioned.
  • Cannot re-enable a toy the operator disabled: 403 disabled_by_operator.

Operator kill switch admin

  • Disable with a required reason, enable, revoke (lost, stolen, compromised, retired).
  • Reissue a claim code for a lost card, only while the toy is unclaimed.
  • Rotate a secret from the CLI; the old one keeps working for 7 days so the bench can reflash.

Parent accounts

Registering creates a family and its first (owner) login in one transaction. Passwords are hashed with Node's built-in scrypt, with the parameters stored inside the hash string, so the cost can be raised later and old hashes still verify. A login attempt for an unknown email still runs the hash against a dummy value, so the response time and body are identical whether or not the account exists.

The session is two tokens: a 15-minute access JWT that carries the family id (so no database hit per request) and an opaque 30-day refresh token, of which only the SHA-256 is stored. Refreshing rotates it, and rotation is what makes theft visible:

Login and register are rate limited in Redis (10 per 15 minutes per IP and email; 5 registrations per hour per IP). Unlike the device side, these limits fail open when Redis is down: locking every parent out because a cache is unavailable would be worse than a short window without brute-force protection, and a parent request cannot spend credits.

The data model

Seven tables, all uuid keyed, created by one forward-only SQL migration. The vector extension is enabled now so the memory tables that arrive later never need a superuser step.

One check in the devices table encodes a rule the code also enforces: status = 'disabled' holds exactly when disabled_by is set, so the "who disabled it" question always has an answer. The rule "a toy's child belongs to the toy's family" lives only in the registry: as a CHECK it broke family deletion, because Postgres clears family_id and child_id through two separate cascades it cannot order.

Every error is { "error": { "code", "message", ... } } with an x-request-id header; device errors add server_time. Logs carry ids and codes only, never a signature, nonce, email or a child's words.

Where things live

Store modules are SQL only; every business rule sits in devices/registry.js or auth/service.js. Repository functions take the queryable (pool or transaction client) as their first argument, so whether a call is inside a transaction is visible at the call site.

config.js
Reads the environment once, freezes it, and refuses to boot in production on default secrets, a placeholder KEK, or DEVICE_AUTH=off.
devices/signing.js
The pure half: canonical string, HMAC, nonce. Shared by the server, the simulator and the test vectors.
devices/hmac_auth.js
The verifier (the seven steps above) and the header/query extractor.
devices/registry.js
Provisioning, claim, disable/enable, unpair, revoke, reissue, rotate, and the blocked-socket hook.
devices/secret_box.js
AES-GCM sealing of secrets and peppered claim-code hashing, both under HKDF subkeys of DEVICE_KEK.
devices/sim_client.js
SimDevice: signs exactly like firmware; used by the tests and npm run e2e.
middleware/device_auth.js
deviceAuth and requireActive for Express; captures raw body bytes for the signature.
ws/stream.js
The /v1/stream upgrade, the ready message, and the socket map the kill switch closes.
routes/device.js
GET /v1/time, POST /v1/heartbeat.
routes/dashboard.js
Everything under /api: auth, children, claim, device management.
routes/admin.js
Batches, device search, force-disable, revoke, reissue claim code.
auth/
scrypt passwords, JWT and refresh tokens, register/login/refresh/logout.

scripts/

Unit tests for the pure parts; integration tests against real Postgres and Redis in a separate littlebuddy_test database.

Running it

docker compose up -d          # Postgres (pgvector) + Redis
cd backend
npm install
copy .env.example .env
npm run migrate
npm test                      # 99 tests; fails fast with a hint if Docker is off
npm run seed                  # demo family, one claimed toy, one unclaimed toy
npm run e2e                   # a simulated toy through its whole life
npm run dev                   # http://localhost:3000/healthz

The seed prints a parent login (demo@littlebuddy.local / demo-password), a claimed toy's id and secret (also written to backend/.env.device), and the claim code of a second, unclaimed toy, so the whole flow can be driven by hand with SimDevice and curl.
